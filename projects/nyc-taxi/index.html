The checkpointed warehouse occupied 8.55 GiB, including raw, candidate and consumer data. Publication copied eight tables before committing their version together. That extra copy buys a clear failure boundary; it has a measurable runtime and storage cost.

One local Windows run with warm input cache and a new warehouse. Total time includes loading, dbt, checks and publication; it excludes downloads and preparation checksums. RSS sums the pipeline and child processes and can double-count shared pages or miss short peaks. A 4 GB DuckDB budget applied separately to ingestion and dbt, not total process RSS. This is not a speedup comparison or a cloud cost benchmark.

What the failure tests prove

The current publisher validates a candidate, then replaces eight consumer tables and their version metadata in one DuckDB transaction.

  • Invalid candidate: mismatched counts or mart totals are refused; the previous consumer relations remain unchanged.
  • Interrupted copy: injected exceptions during copying or before commit preserve every previous consumer relation.
  • Abrupt process exit: reopening the database finds the previous release intact; a subsequent valid publication succeeds.

Failure tests use generated candidates and sample integration data, separately from the full-data measurement. This is a single-writer warehouse running locally, in Docker and in CI; no live cloud mart is claimed.

Change a source. Keep the consumer contract.

A six-scenario exercise on 30,000 public sample rows tests the maintenance path: review affected months and outputs, bind the plan to source bytes and the current publication, then apply it.

  • Correct January: a changed amount and an extra nullable source column reload January alone. February's classification checksum remains unchanged; downstream marts are rebuilt together.
  • Reject a breaking schema or bad candidate: a missing required column is refused before apply. Injected negative fares fail the quality gate; all eight consumer tables and their version remain unchanged. Restoring valid input publishes successfully.
  • Change the business rule: lowering the distance threshold reclassifies both loaded months without reloading sources. The published facts satisfy the new rule.

Corrections and faults are generated exercises, not real TLC incidents. Source reloads are selective; downstream tables rebuild in full. The plan is a single-writer safeguard, not distributed concurrency control.
